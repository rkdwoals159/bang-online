## 발견 사항과 수정 방향

### A01. 조회 실패가 SSE 복구와 분리되어 화면이 멈출 수 있다

**위치:** `apps/web/src/transport/sites-client.ts:737`, `:753`, `:674`; `apps/web/src/app/pages.tsx:83`, `:301`.

SSE invalidation의 버전을 hint에 저장한 다음 sync를 요청한다. 이 조회가 HTTP 500으로 실패하면 `INVALID_RESPONSE`를 기록하고 종료한다. SSE 연결은 계속 `connected`이고, fallback 조회는 연결이 끊긴 경우에만 반복한다. 같은 버전의 다음 invalidation도 이미 저장한 hint 때문에 무시한다. 화면 쪽 자동 재시도는 `CONNECTION` 오류에만 적용된다.

**재현:** 최초 캐시 version 1 → version 2 알림 → 조회 한 번만 500 → 정상 연결 유지 → version 2 알림 재수신. 캐시는 계속 version 1, 재수신 후 추가 조회 0회, 마지막 오류는 `INVALID_RESPONSE`였다. 다른 플레이어가 마지막 행동을 끝내고 이 사용자의 응답을 기다리는 상황이면 진행에 필요한 선택이 도착하지 않을 수 있다. SSE 재접속·새 버전 행동·수동 조회가 우연히 발생하면 복구될 수 있으므로 모든 조회 실패가 영구 정지한다고 주장하지 않는다.

**수정 방향:** SSE 연결 상태와 별개로 미해결 hint의 조회를 제한된 지수 지연으로 재시도한다. 5xx를 잘못된 DTO와 구분하고, 성공한 최신 조회 뒤 hint를 해소한다. 숨김/구독 종료/권한 거절은 재시도 종료 조건으로 둔다. 한 번 실패 후 서버가 회복하고 추가 게임 이벤트가 없어도 복구되는 회귀 케이스가 필요하다.

**근거:** [transport 재현](transport-reproductions.json), [스크립트](transport-reproductions.mjs).

### A02. 동시 대응 ACK가 공개 기록을 유실시킨다

**위치:** `apps/site/src/server/matches/service.ts:391`; `apps/web/src/transport/sites-client.ts:581`, `:644`; `apps/web/src/transport/state.ts:161`.

서버의 새 명령 ACK에는 해당 명령에서 만든 이벤트만 포함된다. 클라이언트는 ACK snapshot과 함께 match의 `eventSeq`를 즉시 최신으로 올린다. 그런데 개틀링/인디언은 이전 버전에서 만든 독립 응답도 최신 상태에서 허용한다. 따라서 그 사이 다른 사람이 만든 이벤트를 받지 못했어도 커서가 앞서간다. 다음 sync는 앞서간 커서 이후만 요청하고 `unchanged`를 받으므로 빠진 공개 기록을 다시 가져오지 않는다.

**실제 D1 재현:** 인디언 직후 커서 4를 가진 후순위 플레이어 → 첫 대상이 피해 수락해 공개 `INDIANS_HIT` seq 5 생성 → 후순위 플레이어가 이전 버전의 유효한 응답 제출 → ACK 적용 후 커서 8 → 재조회. 서버에는 seq 5가 있지만 해당 사용자의 공개 기록에는 없었다. 뒤쪽 다른 피해 기록은 수신되어 화면만 보면 유실을 알아차리기 어렵다.

HP 판정은 서버에서 정확하게 반영되지만 기록·효과음·방어/피해 결과 연출이 빠질 수 있다. 다른 플레이어보다 기록이 적게 남는 원인이 된다.

**수정 방향:** 게임 snapshot의 최신 버전과 이벤트를 연속 수신한 커서를 분리하거나, ACK에 delta의 기준 커서를 명시해 간격이 있으면 기존 커서부터 보충 조회한다. 공개 이벤트에는 비공개 이벤트에 따른 seq 공백이 정상적으로 있으므로 공개 목록의 숫자 공백만 보고 유실로 판단하면 안 된다.

**근거:** [실제 D1 결과](ack-gap-d1.json), [실제 경로 재현 스크립트](ack-gap-d1.mjs), [간단한 transport 재현](transport-reproductions.json).

### A03. 초대 링크가 브라우저 상태와 최초 응답에만 의존한다

**위치:** `apps/web/src/app/app-state.tsx:84`, `:197`; `apps/site/src/server/rooms/service.ts:188`; `apps/web/src/features/room-entry/RoomEntry.tsx:184`.

초대 토큰은 React 메모리에만 보관한다. 새로고침하면 그 값이 사라진다. 서버는 초대 hash만 저장하고, 생성 명령의 중복 응답에는 `inviteCode: null`을 돌려주며, 좌석 복구 응답에도 토큰이 없다. 방 생성이 저장된 직후 응답을 놓친 경우에도 같은 문제가 생긴다. 현재 UI는 새 방을 만들라고 안내한다. 기존 좌석 복구는 되지만 친구에게 줄 초대 링크는 복구되지 않는다.

**수정 방향:** 이미 받은 링크는 브라우저 재시작 정책에 맞게 보존하고, 방장이 현재 방에서 새 초대를 발급받을 수 있는 경로를 마련한다. 최초 응답 유실은 브라우저 저장만으로 해결되지 않는다. 재발급 시 기존 링크 유지/무효화 정책을 명시해야 한다. raw token을 모든 RoomView에 넣는 방식은 피한다.

**근거:** [D1 재현 결과](d1-reproductions.json)의 A03. 최초 생성은 토큰을 반환했지만 재전송은 null, 복구는 토큰 필드 없음.

### A04. 결투에서 개시자가 자신에게 총을 쏜다

**위치:** `apps/web/src/features/experience/model.ts:61`; `packages/engine/src/effects/cards/duel.ts:149`; `apps/server/src/projections/sync.ts`의 `DUEL_BANG_PLAYED` 허용 필드.

공개 결투 이벤트의 `responderPlayerId`는 이번에 뱅을 낸 사람이다. 연출은 개시자가 뱅을 내면 이 responder를 상대라고 선택한다. 이 시점에는 개시자와 responder가 같은 사람이므로 자기 자신을 대상으로 총탄을 그린다. 상대가 뱅을 내는 첫 응사는 올바르지만 개시자의 응사부터 잘못된다. 규칙 판정/피해는 별개로 정상이다.

**수정 방향:** 서버 이벤트에 결투 상대의 공개 player ID를 명시하고 허용 목록으로 전달하여 연출이 그 값을 사용하게 한다. 양쪽이 번갈아 두 번 이상 뱅을 내는 테스트에서 매번 actor와 target이 다름을 확인한다.

**근거:** [실제 엔진 기반 재현](duel-presentation-reproduction.json): actor `player-A`, 실제 연출 target `player-A`, 기대 target `player-B`.

### A05. 강퇴당한 사용자에게 이전 대기실이 남는다

**위치:** `apps/web/src/transport/sites-client.ts:600`; `apps/web/src/app/pages.tsx:355`, `:79`.

회원 권한 거절을 받으면 transport는 `SYNC_REJECTED`만 기록하고 해당 room 캐시를 유지한다. 페이지는 room이 없는 경우에만 이 오류를 방 이용 불가 화면으로 처리한다. room이 캐시에 있으면 기존 대기실을 계속 그린다. 입력 허용 검사도 `CONNECTION`만 오류로 다뤄 이 캐시의 버튼을 활성화할 수 있다. 서버는 권한 없는 명령을 거절하므로 권한 우회가 확인된 것은 아니다.

**수정 방향:** room별 동기화/권한 오류를 관리하고, 확인된 소속 상실은 그 room 캐시와 구독을 종료하며 화면을 참가 종료 상태로 전환한다. 세션 자체 상실과 방에서의 강퇴도 구분한다. 단순 서버 5xx 때문에 회원 정보를 삭제하지 않도록 A01과 함께 설계한다.

**근거:** [transport 재현](transport-reproductions.json)의 A05에서 권한 거절 후 캐시와 이전 member ID가 그대로 남았다. 최종 화면 분기는 정적 코드 확인이며 이번 검토에서 실제 두 브라우저 강퇴 화면은 실행하지 않았다.

### A06. 과거/닫힌 방의 구독과 API 호출이 계속 남는다

**위치:** `apps/web/src/app/app-state.tsx:87`, `:103`; `apps/site/src/storage/repository.ts:808`; `apps/web/src/transport/sites-client.ts:774`, `:829`.

최상위 provider는 복구한 모든 방에 `watchRoom`을 등록한다. 현재 경로에 대한 별도 구독을 더해도 기존 전체 구독은 유지된다. 서버의 복구 목록에는 closed 방도 포함된다. transport의 복구 함수가 내부에서는 closed를 제외하더라도 반환한 전체 목록을 provider가 다시 watch하므로 제외 처리가 무효가 된다.

닫힌 방만 구독하는 SSE는 서버 소속 검사에서 연결을 거절한다. 클라이언트는 이 resource를 제거하지 않고 SSE 재접속과 HTTP fallback 조회를 반복할 수 있다. 활성 과거 방은 접속 표시까지 갱신되어 실제 그 방을 보고 있지 않아도 연결된 참가자로 보일 수 있다. 여러 방을 만든 오래된 브라우저에서는 불필요한 상태 조회와 화면 store 업데이트가 누적된다.

**수정 방향:** 홈의 좌석 복구 목록과 현재 게임의 실시간 구독을 분리한다. closed 방은 실시간 구독에서 제외하고, 현재 경로/의도한 관찰 대상만 유지한다. SSE의 최대 32개 resource 절단도 정상 구독 정책으로 해결해야 한다. 운영 지연이나 D1 요금의 감소량은 계측 전까지 수치로 주장하지 않는다.

**근거:** [D1 복구 결과](d1-reproductions.json)의 A06은 closed 방을 반환했다. 재구독 및 반복 조회 조건은 위 코드 경로에서 확인했다.

### A07. 초대 제한의 대기 시각과 유휴 초기화가 틀린다

**위치:** `apps/site/src/storage/invite-limiter.ts:134`, `:137`, `:247`; 기준 `outputs/development-plan/04_PROTOCOL.md:496`.

reserve는 최근 60초 실패 수와 진행 중 예약 수만으로 거절 여부를 정한다. 실패가 만료되면 아직 미래인 `retryAt`을 무시하고 즉시 허용한다. 반대로 15분 유휴 후 지연 단계 초기화는 별도 prune에만 있고 요청 경로에서는 적용되지 않는다. 현재 Site 요청 경로에 prune 호출은 없다.

**고정 시계 재현:** 반복 제한 후 `retryAt=901001`인데 시간 `62000`의 요청이 허용됐다. 이후 15분 넘게 쉬고 새 실패 5회가 발생했을 때 첫 제한이 정책의 1초 대신 900000ms(15분)였다. 공격 방어 제한은 빨리 풀리고, 정상 사용자는 오래된 지연 단계를 이어받을 수 있다.

**수정 방향:** reserve에서 rolling 실패 만료, 15분 유휴 초기화, 미래 retryAt 검사 순서를 명시적으로 적용한다. 유지보수 prune 실행 여부에 정확성이 의존하지 않도록 한다. 경계 시각/성공 JOIN 초기화/동시 예약 회귀 테스트를 추가한다.

**근거:** [D1 재현](d1-reproductions.json)의 A07.

### A08. 기존 Node 테스트가 현재 준비 정책을 반영하지 못했다

**위치:** `apps/server/test/runtime/runtime.test.ts:259`, `:381`; 기준 `01_RULES.md` D12.

1. 자동 준비된 방에 `SET_READY(true)`를 다시 보내고 version 1의 변경 알림을 기대한다. 현재 명령은 no-op이므로 변경 알림이 없어 timeout이 난다.
2. 4명이 모였지만 준비 버튼을 안 눌렀다는 이유로 시작 거절을 기대한다. D12에 따라 현재 구현은 정상적으로 시작해 `in_game`을 반환한다.

이는 이번 실행에서 발견한 **테스트 기대값 오류**다. 운영 Sites 준비 정책의 버그로 분류하지 않는다. 다만 전체 테스트를 PASS로 보고하거나 오래된 테스트를 건너뛰는 것은 잘못이다. no-op 알림 정책을 검사하고, 자동 준비 상태에서 시작 성공을 검증하는 현재 정책의 시나리오로 갱신해야 한다.

**근거:** [전체 회귀 로그](logs/regression.log). 786개 중 784 PASS / 2 FAIL.

## 성능 개선 후보 A09: 시드의 치명상 구제 옵션 폭증

**위치:** `packages/engine/src/effects/runtime/index.ts:942`; `apps/web/src/features/reactions/ReactionPrompt.tsx` 옵션 렌더.

일반 턴의 시드 능력은 비용 선택기를 쓰지만 치명상 구제는 여전히 손패 두 장의 모든 조합을 옵션으로 만든다. 손패 20장인 실제 엔진 fixture에서 시드 옵션 **190개**, 탈락 수락 포함 **191개**, 본인 snapshot **35,946 bytes**였다. 각 두 장 옵션을 현재 UI로 표현하면 카드 이미지 참조가 **380개** 생긴다. CDN 이미지 캐시는 중복 다운로드를 줄이지만 옵션·DOM 비용은 남는다.

정상 규칙 동작이며 이번에 측정한 서버 장애는 아니다. 두 장을 고르는 단일 비용 선택기로 정리하면 UI·응답 크기를 줄일 수 있다. 서버의 정확한 두 장 비용 검증과 구제 후 반복 회복은 보존해야 한다. [측정 결과](sid-rescue-measurement.json). 운영 P95나 실제 모바일 렌더 시간은 측정하지 않았다.

## 권장 수정 순서

1. A01 조회 재시도와 A02 snapshot/이벤트 커서 처리부터 고친다.
2. A05 권한 상실 상태, A06 구독 수명, A03 초대 복구를 정리한다.
3. A07 제한 시간 정책과 A04 결투 연출을 고친다.
4. A08 테스트 기대값을 현재 정책으로 갱신하고 전체 회귀를 다시 실행한다.
5. A09 구제 비용 선택기를 개선하고 실제 모바일 화면에서 확인한다.

수정 후에는 동일 공격의 여러 플레이어 대응, 한 번의 5xx 후 무이벤트 복구, 새로고침/응답 유실 후 초대, 강퇴 사용자 화면, 닫힌 방의 구독 정리, 양방향 결투를 실제 로컬 브라우저 흐름으로 검증해야 한다.
