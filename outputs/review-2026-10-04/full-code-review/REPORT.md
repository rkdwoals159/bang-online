## 1. 결론과 검토 기준

검토 기준 커밋: `01825f523e45e0747f2b5a6a324f66d1a4590a21`. 시작 시 작업 트리는 깨끗했다. 규칙 기준은 기존 `01_RULES.md`의 R01–R30, C01–C16, 명시적 구현 결정이다. 새 규칙을 가정하지 않았다.

이번 결과는 **정적 코드 검토**다. 아래 재현 경로는 코드로 추적한 조건이며 실제 브라우저에서 새로 실행한 재현 결과가 아니다. 테스트, 빌드, 운영 DB 변경, 배포를 실행하지 않았다. 테스트 통과 숫자를 새로 기록하지 않았다. 애플리케이션 소스는 수정하지 않았으며 이 보고서만 추가했다.

검토한 주요 경로:

- 엔진: 초기 배분, 거리와 사거리, 행동 후보와 명령 검증, 카드 이동, 판정, 응답 저장·재개, 피해·구제·탈락·보상·승리, 턴 시작과 드로우.
- 카드·인물: 기본 행동, 장비, 감옥, 다이너마이트·술통, 결투, 개틀링·인디언, 잡화점, 패닉·캣 벌루, 손패 정리 및 인물 능력 호출 지점.
- 서버: 현재 운영하는 Sites Worker의 인증, 대기실, 매치 명령, D1 저장과 명령 영수증, 조회·동기화·SSE. 공유하는 Node 서버의 턴 런타임과 공개 이벤트 투영도 확인했다.
- 화면: 라우팅, 참여 복구, 카드 행동·응답, 대기실, 게임판, 결과·기록, 카드 상세, Sites HTTP/SSE 클라이언트와 상태 저장소.
- 기존 테스트: 주요 분기와 수락 기준을 읽고 검토 결과와 비교했다. 모든 테스트 파일의 모든 assertion을 검토하거나 모든 분기를 실행한 것은 아니다.

## 3. 결함 상세

### R01 — 결투 사용자 탈락 후 게임 진행 중단

**코드 근거:** [턴 자동 진행](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/apps/server/src/commands/turn-runtime.ts:97), [효과 종료](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/effects/runtime/index.ts:1557), [탈락한 현재 플레이어 거부](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/turn/reducer.ts:46).

`runQueue()`는 피해와 탈락, 후처리, 승리 판정까지 끝내지만 살아 있는 다음 플레이어로 턴을 이동하지 않는다. 서버의 `advanceTurnPhases()`는 `phase !== "start"`이면 즉시 반환한다. 탈락한 현재 플레이어를 건너뛰는 분기는 그 뒤에 있어 `play` 단계의 탈락에는 적용되지 않는다.

코드상 재현 조건:

1. 현재 무법자 A가 HP 1이고, 보안관·다른 무법자·배신자가 살아 있다.
2. A가 결투를 사용하고 상대가 뱅을 버린다. A는 대응할 수 없거나 포기한다.
3. A가 구제 없이 탈락한다. 보안관 생존 및 적대 진영 생존으로 게임은 종료되지 않는다.
4. 상태는 `playing`, `turn.phase = play`, `turn.currentPlayerId = A`로 남는다.
5. A는 탈락하여 행동할 수 없고, 다른 사람은 자기 턴이 아니므로 행동할 수 없다.

**수정 방향:** 효과 큐·탈락 후처리·승리 판정이 끝난 경계에서, 현재 플레이어가 탈락했고 게임이 계속된다면 다음 생존자로 이동한다. 개틀링 같은 다중 대상 효과 해결 도중에는 턴을 넘기지 않는다. 그 뒤 정상 턴 시작·드로우를 한 번만 실행한다.

### R02 — 럭키 듀크 감옥 실패 결과의 유실

**코드 근거:** [감옥 완료 이벤트](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/effects/cards/jail.ts:327), [이벤트 적용](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/effects/runtime/index.ts:330), [턴 시작의 지역 변수](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/turn/draw.ts:174).

일반 감옥 판정에서는 `resolveTurnStart()`가 같은 호출에서 나온 `JAIL_JUDGMENT_RESOLVED.turnSkipped`를 보고 턴을 생략한다. 럭키의 경우 첫 호출은 선택을 저장하고 반환한다. 응답 후 효과 런타임은 감옥을 버리고 실패 이벤트를 만들지만, 그 이벤트는 턴 상태에 적용되지 않는다. 다시 턴 시작을 실행하면 감옥이 이미 없어서 `jailSkippedTurn = false`로 드로우를 진행한다. R05 위반이다.

**재현 조건:** 럭키가 감옥에 갇힌 상태에서 후보 두 장이 모두 비하트이거나 비하트를 선택한다. 응답 후 드로우·카드 사용 단계에 진입하는 경로가 있다.

**수정 방향:** 감옥 판정 결과를 저장 가능한 턴 시작 후속 상태로 유지하고, 동기 판정과 저장된 선택 재개가 동일한 턴 전환을 사용하게 한다. 과거 공개 로그를 훑어 판정 결과를 추정하는 방식은 피한다.

**기존 테스트의 빈틈:** [Lucky Jail 테스트](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/test/turn/draw.test.ts:351)는 비하트와 하트를 준비하지만 실제 응답은 하트를 선택한다. 실패 후 턴 생략을 검증하지 않는다.

### R03 — 인물 선택에 필요한 카드 정보 누락

**코드 근거:** [응답 DTO 투영](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/state/projection.ts:43), [잡화점에만 공개 풀 제공](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/state/projection.ts:192), [화면에서 볼 수 있는 카드 목록](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/apps/web/src/features/reactions/model.ts:151).

KIT_PICK / LUCKY_DRAW의 응답 옵션에는 후보 카드 ID가 있지만 후보는 자기 손패에 있지 않다. 응답 화면이 이름을 조회하는 목록은 자기 손패와 잡화점 카드뿐이다. 따라서 후보의 종류·숫자·문양을 확인하여 선택할 수 없다. 잡화점 수정으로 이 두 인물의 선택까지 해결된 것은 아니다.

- 킷 칼슨: 덱 위 세 장을 **본인만** 확인해야 한다(C07). 현재 자기 응답 DTO에도 세 장의 카드 정보가 없다.
- 럭키 듀크: 판정 후보 두 장을 **모두에게 공개**해야 한다(C08). 현재 공개 테이블에는 없고, 후보를 풀로 이동시키는 `CARD_TRANSFERRED` 이벤트도 공개 이벤트 투영에서 제외된다.
- 럭키의 선택 완료 후 판정 카드 한 장 공개와, 선택 전에 두 후보를 공개하는 것은 별개의 요구사항이다.

**수정 방향:** 선택 카드 DTO에 공개 범위를 명시한다. 킷의 세 장은 현재 응답자에게만, 럭키의 두 장은 공개 판정 정보로 전달한다. 선택 카드, 판정 목적, 두 장의 버림 순서를 화면에 표시한다. 일반 덱이나 다른 사람의 손패를 DTO에 추가해서는 안 된다.

### R04 — 수지 라파예트의 빈 손패 확인 누락

**코드 근거:** [지원 응답 종류 제한](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/effects/runtime/index.ts:555), [효과 사용자만 검사](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/effects/runtime/index.ts:623), [카드 이동 처리](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/packages/engine/src/effects/runtime/index.ts:330).

빈 손패 훅은 뱅·개틀링·인디언 응답 또는 해당 효과의 사용자 수지에 대해서만 실행된다. 결투 상대편 수지는 `DUEL_RESPONSE`가 훅 대상에서 빠지고, 효과 완료 시에도 사용자가 아니므로 검사되지 않는다. 다른 플레이어가 수지의 마지막 손패를 패닉으로 가져가거나 캣 벌루로 버리는 경우에도 카드 이동 후 수지를 검사하는 경로가 없다. 제시의 드로우 탈취도 같은 누락을 검토해야 한다.

**재현 조건:** 수지 B의 손패가 뱅 한 장이고 A의 결투에 응답하여 그 카드를 버린 뒤 결투가 종료된다. 또는 상대가 수지의 마지막 손패를 가져간다. 살아 있는 수지의 손패가 0으로 남지만 C14 드로우가 발생하지 않는다.

**수정 방향:** 카드 이동의 영향을 받은 플레이어와, 효과 완료까지 보류할 빈 손패 능력을 함께 추적한다. 결투는 종료 경계에서 참가자의 빈 손패를 확인한다. 마지막 역마차·웰스 파고·잡화점 효과 후 불필요한 추가 드로우가 없어야 하고, 슬랩 대응 중 마지막 빗나감의 즉시 드로우 및 D11의 엘 그링고 순서를 보존해야 한다.

### R09 — EventSource 생성 실패 후 자동 갱신이 없어짐

**코드 근거:** [생성 실패 catch](C:/Users/user/Documents/Codex/2026-09-27/new-chat-2/apps/web/src/transport/sites-client.ts:745).

EventSource 생성자가 예외를 던지면 disconnected 상태만 설정하고 반환한다. 스트림이 열린 뒤 발생하는 오류에는 재연결 처리가 있지만 생성 실패에는 재시도 예약이나 HTTP 주기 조회가 없다. HTTP 행동은 가능한 구조이므로, 본인 행동만 갱신되고 타인의 행동은 자동 반영되지 않는 상태가 생길 수 있다. 일반적인 지원 브라우저에서 늘 발생하는 문제라는 뜻은 아니다.

### 페이지 전체 리로드에 대한 결론

카드 행동의 정상 경로에는 `location.reload()`나 페이지 전체 이동이 없다. 라우팅은 History API를 사용한다. 확인한 명시적 리로드는 오류 화면의 사용자 재시도 버튼이다. 따라서 이전에 느낀 화면 전체 리로드를 코드만으로 실제 문서 재로드라고 확정할 수 없다.

대신 상태 갱신에 따른 여러 패널 렌더, 연결 복구의 입력 잠금, 결과 전환의 컴포넌트 교체는 존재한다. 실제 문서 요청 발생 여부와 레이아웃·스크롤 변화는 브라우저 Network/Performance 기록으로 따로 확인해야 한다.

## 5. 확인한 방어와 검토 한계

- 매치·방 명령에는 버전 확인과 명령 ID/요청 해시 영수증이 있다. D1 변경은 commit guard와 batch로 묶는다. 정적 검토에서 같은 버전의 명령이 무조건 중복 적용된다는 결론은 나오지 않았다. 실제 Worker·다중 브라우저 경쟁 조건은 별도 검증이 필요하다.
- 공개 DTO는 허용 목록 방식이며 상대 손패·역할·덱 전체를 그대로 전송하지 않는다. 이 설계는 유지해야 한다. R03/R05는 필요한 공개·개인 선택 정보까지 빠지는 문제다. 모든 응답·오류·로그의 비공개 정보 검증을 완료했다는 뜻은 아니다.
- 최신 버전·eventSeq·viewer 확인, 요청 합치기, bounded 공개 기록, SSE 재연결 코드가 이미 있다. 이들의 존재가 이번에 발견한 재개 분기·기록 의미 충돌을 막지는 못했다.
- 만피 맥주의 일반 사용은 R14와 사용자의 기존 결정에 따라 유지 대상이다. 회복 0 확인 UI도 유지한다. 만피 사용 자체를 새 규칙으로 금지하지 않는다.
- 기존 잡화점 카드 이름 수정은 남아 있다. R03은 다른 종류의 선택 프롬프트 문제다.
