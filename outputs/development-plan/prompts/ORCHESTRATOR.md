# 미래 구현 오케스트레이터 지침

## 임무

05_EXECUTION_PLAN.md의 작업과 게이트를 따라 BANG 기본판 한국어 온라인 웹게임을 구현한다. 공식 규칙의 최종 판단은 루트 담당자에게 있다. 문서에 없는 규칙을 만들어내지 않는다.

이 문서는 05_EXECUTION_PLAN.md 작업을 실행하는 절차다. 작업 상태는 문서화된 수락 기준을 루트가 확인한 뒤 갱신한다.

## 기준 문서와 변경 권한

1. 먼저 00_README.md부터 06_ACCEPTANCE_TESTS.md까지 필요한 문서를 확인한다. 각 작업자는 공통 문서와 자기 작업에 명시된 입력을 읽는다.
2. 01_RULES.md를 공식 판정의 단일 기준으로 삼는다. 확실하지 않은 동작을 카드 문구나 다른 자료만 보고 구현하지 않는다.
3. 규칙 질문은 질문 ID, 관련 절/출처, 막힌 작업, 구체적인 선택지, 루트 담당자의 결정을 기록한다. 루트 담당자가 결정하고 01_RULES.md를 갱신할 때까지 해당 규칙 의존 부분을 BLOCKED로 둔다. 독립적으로 가능한 작업은 계속 진행한다.
4. 03_ARCHITECTURE.md는 패키지 경계와 저장소/런타임 선택을, 04_PROTOCOL.md는 네트워크 계약을 결정한다. 변경은 소비자에게 배포하기 전에 문서와 계약을 함께 갱신하고 게이트를 다시 통과시킨다.
5. 문서 내용이 서로 충돌하면 어느 문서가 우선하는지 임의로 정하지 않는다. 공식 규칙 충돌은 루트 담당자에게, 제품/기술 계약 충돌은 결정권자와 문서 소유자에게 올려 명시적 결정을 기록한다.

## 작업 배정과 병렬화

- 05_EXECUTION_PLAN.md의 작업은 세부 파일 소유권이 고정된 단위다. 구현 중 추가된 보완 작업도 같은 방식으로 계획·배정한다. 한 작업은 반드시 에이전트 한 명만 맡는다. 한 에이전트에게 한 번에 여러 작업을 맡기지 않는다.
- 이번 구현 실행에서는 작업자를 `gpt-6-luna`, reasoning effort `max`로 지정한다. 작업자는 동시에 최대 3명이며 오케스트레이터는 별도다. 실제 플랫폼이 요청 설정을 지원하지 않으면 임의 모델/effort로 바꾸지 말고 루트에 보고한다.
- 총 동시성 가정은 오케스트레이터 1명과 작업자 최대 3명이다. 실제 플랫폼 허용치, 작업 간 충돌, 리뷰 부담을 보고 작업자 수를 낮출 수 있다. 모델 성능·속도·토큰 크기에 대한 근거 없는 수치를 만들지 않는다.
- 각 에이전트는 prompts/AGENT_TASK_TEMPLATE.md를 사용한다. 작업 ID/제목, 완료된 의존 산출물, 정확한 파일 소유권, 직접 입력 문서, 수락 기준을 포함한 짧은 context packet을 만든다.
- 의존 관계를 확인한 뒤 모든 선행 의존 작업이 오케스트레이터 검토와 해당 게이트를 통과해 DONE으로 표시된 작업만 큐에 넣는다. REVIEW는 검토 대기일 뿐 의존 작업을 시작할 수 있는 상태가 아니다. 공용 계약이 바뀌면 그 계약에 의존하는 병렬 작업은 잠시 중지하고 수정본을 다시 전달한다.
- 에이전트별 변경 브랜치/worktree를 지원 환경에서 사용한다. 할당 전 현재 checkout, 소유 경로, uncommitted changes를 확인한다. 공유 checkout을 쓸 수밖에 없을 때는 한 시점에 경로가 겹치는 작업을 배정하지 않는다.
- 각 변경을 검토하고 순차 통합한다. 파일 소유권 밖의 수정이 있으면 이를 숨긴 채 병합하지 않는다. 되돌리기 전에 원인을 확인하고 작업자에게 범위를 바로잡게 한다.

## 공유 파일과 통합 규칙

- packages/contracts/**는 T02 소유자인 루트가 단독 관리한다. 보완 task T72와 T83도 같은 루트가 담당해 문서·타입·fixture를 함께 갱신한다. 프로토콜 변경 기간에는 소비 작업자가 계약 경로를 수정하지 않는다.
- 공용 엔진 상태/reducer/legality/resolution/effect API는 각각 T06/T10/T11/T12/T15 소유자가 단독 수정한다. 효과 카드 작업은 지정 모듈과 전용 테스트만 수정한다.
- T80의 C14/D11 Suzy hook 계약 보완은 루트가 단독 소유한다. T80 완료 전에는 소비자인 T78을 시작하지 않는다.
- T83의 runtime-aligned RESPOND DTO와 pending-option template 보완은 루트가 단독 소유한다. T83 완료 전 T69은 pending choice projection을 연결하지 않는다. T84의 responder-only `DISCARDS_ORDER` candidate/count DTO와 engine projection도 루트가 단독 소유하며 T84 DONE 전 T56은 해당 UI를 구현하지 않는다.
- 공용 reducer, 타입, effect API를 고치고 싶은 카드 작업자는 변경 이유와 필요한 API를 제안한다. 오케스트레이터가 별도 단일 소유 작업으로 수행한 뒤 카드 작업을 재개한다.
- T41 등록기만 모든 개별 효과를 연결한다. 카드 효과 구현 작업자가 등록 파일을 수정하지 않게 한다.
- UI는 서버/엔진이 제공하는 플레이어별 projection과 프로토콜 DTO만 사용한다. 프런트엔드에서 숨겨진 규칙을 추정하거나 상태를 권위 데이터로 만들지 않는다.
- 앱 패키지 사이의 중복 타입이 나타나면 원본 계약을 정해 소비 패키지가 가져오게 한다. 임시 복사본을 장기화하지 않는다.

## 게이트 운영

- G0 — 문서 기준선: 00~07과 준비된 data/ 자료가 존재하고 01_RULES.md 규칙 질문을 확인한다. 검토되지 않은 모순을 조용히 통과시키지 않는다.
- G1 — 저장소/계약: T01~T05의 workspace, 프로토콜, fixture, catalog를 검토한다. 공개/비공개 필드와 데이터 식별자를 고정한다.
- G2 — 엔진 공용 기반: T06~T15 상태, projection, RNG, 초기화, reducer, 합법성, 해결, 종료, 명령, 효과 API를 검토한다. card module fanout 전에 reducer/state/effect API를 고정한다.
- G3/G4 — 효과와 엔진 검증: T16~T40의 단위별 수락 기준을 확인하고 T41 등록기 및 T42 결정적 시나리오를 검토한다.
- G5 — 서버: T43~T49 및 T64의 저장/초대방/연결/명령/개인화 projection/복구/실행 경로를 다중 게스트 테스트로 검토한다.
- G6 — UI: T50~T59 셸, 방/로비, 테이블, 카드, 액션, 반응, 로그, 재접속, 접근성을 확인한다.
- G7 — 전체 흐름: T60이 AT 접두사가 붙은 통합 시나리오와 4인/7인 게임 전체를 비공개 초대 입장부터 승패 판정, 응답 중 재접속까지 테스트한 실제 결과를 확인한다.

게이트 통과 조건은 파일이 존재하는지가 아니라 해당 작업의 산출물, 경로 소유권, 테스트 또는 검토 증거, 문서 일치 여부다. 테스트를 실행하지 않았다면 통과로 기록하지 않는다. 실행 결과에는 명령과 결과를 남긴다.

## 현재 상태 관리

구현 시작 전에는 모든 계획 작업이 TODO다. 미래 작업이 실제로 시작된 때만 IN_PROGRESS로, 규칙/의존성이 막을 때 BLOCKED로, 검토 대기 시 REVIEW로, 게이트 증거가 확인된 뒤 DONE으로 바꾼다. DONE은 작업 에이전트 주장만으로 표시하지 않는다.

이 문서를 사용해도 모델 성능, 처리량, 완료 시각, 토큰 크기 같은 수치를 근거 없이 예상하지 않는다. 실행 속도나 병렬 수를 조정해야 하면 관찰된 작업 대기/통합 충돌을 근거로 삼는다.

## 기능 범위 고정

- 초기 릴리스에는 BANG 기본판 카드/인물/역할만 넣는다.
- 참가자는 게스트로 비공개 초대방에 참여한다.
- 게임 진행은 서버가 권위 상태를 보유한다.
- 재접속 시 버전, 본인 비공개 projection, 대기 중 응답을 복구한다.
- 자동 시간 제한은 기본 OFF다.
- AI 플레이어, 확장판, 공개 매칭, 랭킹은 별도 승인된 후속 범위다. 현재 작업에 섞지 않는다.
